# 卸载适用场景与反模式

## 适用场景（默认应卸载）

- 目标不明确的探索式检索
- 需要多轮 WebSearch 的信息搜集
- 大文件的理解与分析（非简单编辑）
- 测试执行与长输出解析
- 依赖影响分析
- Deep Research 多路并行调研（按信息源拆分，确保子问题正交）
- plan 落地——已标注执行位置的多个实现步骤按标注并发派发

## 反模式（不该卸载 / 卸载判断不宜机械）

- 主上下文充裕且 1-2 步可收尾的轻量操作
- 单次即得的简单搜索
- 需要用户实时交互的环节
- **再派停止条件**：主上下文已取得足以支持当前裁决的完整定稿后，额外即席派发应满足以下至少一项：填补一个明确的事实缺口；引入一个可能改变当前裁决的独立评审维度。两项均不满足时，主上下文应直接裁决或收工。独立性按待回答的问题、验收标准或证据源判定；仅更换 agent、模型或复述同一问题不构成独立维度。满足任一项只表示重新套用既有卸载判断，不表示必须派发。本条只约束日常非 team-ops 的额外即席派发；首次派发及 PR/plan review 的专域增量规则保持不变。本条不阻止下一件不同工作的首次派发；评审定稿后的落地不属于再派。

实测补充观察：部分卸载到子 agent 的轻量步骤（精确、1-2 步可收尾），往返+潜在 stall 的开销可能反而高于主上下文直接做，卸载判断不宜太机械——但这是"够用即可"的例外，不是重新囤积的借口；默认仍是卸载，例外要有正当理由。

## 上下文亲和性

同文件集**且**下一步取舍相同的子任务打包给同一 agent，缺一轴就拆。按这两轴拆，不按动作种类。

- **文件集轴**：共享任一文件即视为同文件集，只看直接共享、不做传递闭包；只有完全不重叠才拆多 agent。
- **取舍轴**：先拆后判——先按两轴拆袋，再对每个袋单独判该袋下一步有没有未钉死的取舍。顺序不能颠倒：先选定 agent 再拆，等于按袋内最贵那步定选型。
- **git / PR 不是选型标签**：派发方已钉死的 commit message 与 PR 正文是可执行文本，不构成抬档理由。禁止因为步骤里出现 git / PR 就一律另开一袋。

例：改码规格已钉死、commit message 未钉死 → 拆两袋，各自判：commit 那袋含未钉死的取舍，交给会做取舍的 agent；改码那袋已无取舍，走 econ。
例：改码规格与 commit message 都已钉死 → 同一袋，不拆。

## 并行约束

仅并行信息源不重叠的独立任务；存在数据依赖、操作同一文件、或需顺序验证的步骤禁止并行。
