# 卸载适用场景与反模式

## 适用场景（默认应卸载）

- 目标不明确的探索式检索
- 需要多轮 WebSearch 的信息搜集
- 大文件的理解与分析（非简单编辑）
- 测试执行与长输出解析
- 依赖影响分析
- Deep Research 多路并行调研（按信息源拆分，确保子问题正交）
- plan 落地——已标注执行位置的多个实现步骤按标注并发派发

## 反模式（不该卸载 / 卸载判断不宜机械）

- 主上下文充裕且 1-2 步可收尾的轻量操作
- 单次即得的简单搜索
- 需要用户实时交互的环节

实测补充观察：部分卸载到子 agent 的轻量步骤（精确、1-2 步可收尾），往返+潜在 stall 的开销可能反而高于主上下文直接做，卸载判断不宜太机械——但这是"够用即可"的例外，不是重新囤积的借口；默认仍是卸载，例外要有正当理由。

## 上下文亲和性

同文件集**且**下一步取舍相同的子任务打包给同一 agent，缺一轴就拆。

- 拆分按文件集与取舍两轴，不按动作种类；文件集完全不重叠时拆多 agent。
- 某步含未钉死的取舍时只拆该步，其余步骤保持原 agent 与原模型档；不按袋内最贵那步定选型。
- git / PR / 测试不是选型标签——派发方已写死的 commit message 与 PR 正文是可执行文本，不构成抬档理由。

例：改码规格已钉死、commit message 尚未写死 → 只拆 commit 那一步，改码那截不抬档。
例：改码规格与 commit message 都已写死 → 同一袋，不拆。

## 并行约束

仅并行信息源不重叠的独立任务；存在数据依赖、操作同一文件、或需顺序验证的步骤禁止并行。
