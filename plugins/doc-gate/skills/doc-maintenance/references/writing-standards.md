# 表述规范

本规范参照 ASD-STE100 Simplified Technical English 的 Writing Rules 思路组织条文结构，但**不自称符合 ASD-STE100**——上游规范自身声明「未核对现行版本与词典前不得宣称严格符合」，且社区中常被引用的句长、段长、名词群数量等具体数字未核实到官方 PDF 原文。措辞一律为「参照 STE 思路」，禁止写成「遵循 ASD-STE100」，也不标注任何具体条款号。

分两节，**顺序即优先级**：§A 是硬约束，写作与 review 时必须逐条判定；§B 是次要项，机械可判定，工具化后整体退场。每条附「适用语种」标注，字段含条目陈述、判定要点、正/反例、豁免边界。

## §A 歧义层（硬约束，LLM 必须执行）

### A1　一句一事（中英通用）
每句只承载一个主要动作或陈述，不用从句堆叠塞入多个动作。判定：数一句话里有几个独立可执行动作，超过一个就拆句。
正例：「重启服务。确认端口已监听。」反例：「重启服务并且确认端口已监听，如果没有监听就检查配置文件是否正确加载。」
豁免：枚举清单、条件-动作对（见 A7）允许用列表承载多步骤，本条只约束单句内的动作堆叠。

### A2　明确主语 + 主动动词（中英通用）
句子必须有明确主语，优先用主动动词；施事重要且已知时点名施事，施事未知或不重要才用被动。判定：读者能否一眼看出"谁做了什么"。
正例：「hook 拒绝本次编辑。」反例：「本次编辑被拒绝了。」（施事已知却隐去）
豁免：施事确实未知或对读者无意义时（如"配置文件已损坏"），被动式恰当，不强行补主语。

### A3　术语统一（中英通用）
同一事物在全文用同一术语，不为避免重复而换用同义词。判定：检索同一概念的所有出现处，是否有两个及以上不同表述。
正例：全文统一用「门禁」指代 gate 机制。反例：同一文档中「门禁」「拦截器」「守卫」交替指代同一个 hook。
豁免：A13 豁免的代码标识符、产品名不受本条约束——它们本身唯一，不存在换词问题。

### A4　单一精确含义（中英通用）
用单一精确含义的词；避免习语、俚语、比喻，避免"处理""支持""优化"等含义模糊的万能动词。判定：脱离上下文能否推断出具体动作。
正例：「校验请求体是否符合 schema。」反例：「处理一下这个请求。」
豁免：无——万能动词没有正当例外，遇到即应替换为具体动作。

### A5　术语需定义（中英通用）
精度需要时应使用专业术语，但首次出现须给出定义或链接。判定：不熟悉该领域的读者能否就地理解或一步找到定义。
正例：「BM25（一种词法召回评分算法，见 references/...）」反例：全文反复使用「BM25」却从未解释。
豁免：面向已限定专业读者群的文档（如内部 API 参考）可放宽首次定义要求，但须在文档开头声明前提读者群。

### A6　名词群精简（中英通用）
名词群要短，用介词/助词表明词间关系；中文侧避免"的"字串叠加与修饰语深层嵌套。判定：能否数出 3 个以上连续无助词修饰的名词堆叠。
正例：「用于校验用户权限的中间件」反例：「用户权限校验中间件配置文件路径解析逻辑」
豁免：已固化的复合专有名词（如项目内既定组件名）不强拆。

### A7　程序性文本三要素（中英通用）
程序性文本写成直接指令，明确写出**条件、动作、预期结果**三要素。判定：读者能否照单执行，且知道执行完该看到什么。
正例：「若 `jq` 不可用，脚本 fail-open 直接放行（预期：无 deny 输出）。」反例：「注意 jq 不可用的情况。」（缺动作和预期结果）
豁免：纯说明性段落（非操作步骤）不强制套用三要素结构。

### A8　肯定式优先（中英通用）
优先用肯定式指令，直说读者必须做什么；避免双重否定。判定：句中是否出现两个否定词叠加。
正例：「保留原路径。」反例：「不要不保留原路径。」
豁免：法规/合规类文本要求逐字保留否定表述原文时不改写（见 A13）。

### A9　助动词受控（中英通用）
用「应 / 宜 / 可 / 不应」体系控制强度（对应 shall / should / may / shall not；`can` 表能力不表义务强度，不用作强度词），不混用"建议""最好""尽量"等强度不明的表述。判定：强度词能否明确归入四级中的一级。
正例：「新增文档应补入口索引条目。」反例：「新增文档最好补一下索引，尽量别漏。」
说明：「应/宜/可/不应」体系对应 GB/T 1.1 标准化文件起草规则中的条文用语惯例，此处作**约定**引用——该标准条款原文未取得（付费墙），**不得标注「依据国标 GB/T 1.1 规定」**。豁免：引文、访谈记录等原样转述文本不受约束（见 A13）。

### A10　拼写变体一致（仅英文）
同一文档内不混用 American / British 拼写变体。判定：全文搜索常见变体对（color/colour、behavior/behaviour）是否同时出现两种。
正例：全文统一 American English（`color`, `behavior`）。反例：同一文档中 `color` 与 `colour` 混用。
豁免：直接引用外部文档、代码注释、第三方 API 命名保留原样（见 A13）。

### A11　冠词完整（仅英文）
冠词完整，不用电报体省略。判定：句子读起来是否像被裁剪过的电报。
正例：「Run the script before the deployment.」反例：「Run script before deploy.」
豁免：命令行帮助文本、UI 标签等空间受限场景允许电报体（行业惯例，非本规范豁免，宜就地标注为有意省略）。

### A12　避免悬垂分词（仅英文）
避免 -ing 分词作修饰语造成的悬垂歧义。判定：分词短语的逻辑主语是否与主句主语一致。
正例：「When parsing the config, the script validates each field.」反例：「Parsing the config, each field is validated.」（分词逻辑主语缺失，读者需猜测谁在 parsing）
豁免：无——悬垂分词是纯技术性歧义，没有正当例外。

### A13　豁免条款（防反噬边界，中英通用）
代码、命令、标识符、产品名、法律文本、引文、文件路径**原样保留**，不得为符合本规范而静默简化或改写。判定：改动对象属于以上任一类别时，本规范全体条款（A1-A12、B1-B5）对该对象**不生效**。
正例：保留 `git reset --hard`、`SKILL_GATE_DIR` 等原样不动，即便变量名含"万能动词"或路径含大小写混拼。反例：为了"单一精确含义"把命令 `git commit --amend` 私自改写为口语化描述，破坏可执行性。
本条是防止规范反噬技术内容的边界条款——规范约束叙述性文本，绝不延伸到会破坏可执行性、可追溯性、法律准确性的原始素材。

## §B 排版层（次要，机械可判定）

本节属机械可判定项，优先级低于 §A。将来若安装 `autocorrect` / `zhlint` 等工具，本节整体由工具接管并从 LLM 规范中移除，届时只需删除本节、不触动 §A。

### B1　中英文间加空格（仅中文）
中文与英文/数字之间加一个半角空格。正例：「使用 `jq` 解析 JSON。」反例：「使用`jq`解析JSON。」依据（存在性引用）：sparanoid《中文文案排版指北》。

### B2　标点全半角不混用（仅中文）
中文句子用全角标点，数字与纯英文句内用半角，不混用。正例：「共 3 个步骤（详见下文）。」反例：「共3个步骤(详见下文)。」依据（存在性引用）：GB/T 15834《标点符号用法》、GB/T 15835《出版物上数字用法》。

### B3　不重复标点强调（仅中文）
不重复标点表达强调（禁 `！！！`）。正例：「务必确认无残留。」反例：「务必确认无残留！！！」

### B4　引号/撇号形式一致（仅英文）
引号与撇号形式一致，不混用直引号与弯引号。正例：全文统一用直引号 `"like this"`。反例：同一文档中直引号与弯引号混用。

### B5　连字符区分用途（仅英文）
连字符（-）、en dash（–）、em dash（—）按用途区分，不互相替代。正例：「pre-flight」用连字符；「2020–2024」区间用 en dash；插入语用 em dash。反例：全部用普通连字符替代三种符号。
