# Memory 清理

## 1. 明确范围

确认目标项目、允许改动的路径和删除授权。记录当前未提交内容及保护对象；未经授权不跨项目清理。遇到未知归属的改动或执行中出现冲突，应停止相关修改并报告，不覆盖或恢复他人内容。

## 2. 先判常驻

逐条问：未知任务类型时，这条信息是否仍必须随上下文加载？只让符合此条件的有效偏好和短入口常驻。

有用不等于常驻，独有不等于重要。动态状态、未关闭 Issue、独有事故不自然获得常驻资格；应另按明确用途判断去留。

## 3. 再判去留

读取现行权威，确认其语义已承接旧记忆的有效义务即可，不要求旧清单逐字段复制。已有权威但措辞不同，不应强制复制旧措辞。

用途不明、过时或无法形成可靠结论的普通记忆应直接丢弃，不建待确认库或历史库。独有但用途不明的事故也应丢弃，不以搬家代替删除。

独有的明确用户约束不因年代旧就删除；应保留仍有效的约束。“用户反馈”标签本身不构成永久豁免，仍应核对内容及现行授权。

## 4. 最小承接

只承接明确有用、鲁棒、简洁且可维护的信息。复用已有领域入口；通用 skill 不应塞入项目事实。确有必要且无适当归属时，才使用项目文档。

少量按需路由不等于全量内联。不批量搬运事故，不为已判无用的记忆新建档案库。

## 5. 安全删除

删除前应读取实际内容，核对有效入链和并发改动。应将范围内仍有效的引用改指保留的权威，或移除已无用途的引用，避免断链。

范围外有效引用无法调整时，应保留正文、退出常驻并报告例外，不扩大写入范围。索引退出与正文删除分开决定。

只删除批准范围内已判无用对象，不清空未知目录。执行前应再次确认目标内容未发生并发改动；发生冲突则按第 1 步停止相关修改。

## 6. 验证与短报告

核对实际修改、引用和保护对象。以同一文件集合及编码口径报告清理前后的常驻字节与新增承接内容，分别列明删除、保留、承接位置及例外。

字节数不等于 token 数。静态合同测试不证明模型实际遵循；应说明实际验证范围。文档图谱无 finding 不代表 Memory 已全覆盖。

## 文档协作边界

只复用 doc-maintenance 的文档格式与链接维护要求，不复制其整套流程。

> **前置阅读**：文档格式与引用规则见 doc-maintenance。写入或改写承接文档前，应先读取 [doc-maintenance §2](../doc-maintenance/SKILL.md#2-通用原则) 中的“跨文档引用”要求，以及[表述规范](../doc-maintenance/references/writing-standards.md)。

ARCHIVE 的历史保留流程不应自动适用于已授权丢弃的无用 Memory；此类对象不必归档。

本 skill 不扩大 doc-gate hooks 的覆盖。现有图谱将 Claude Code auto-memory 子树排除；应单独核对 Memory 的链接及删除对象的有效入链，不能以空图谱结果代替检查。
